# Module 06 — Le système d'import de Python

> *The Codex — Mastering Python's Import Mysteries*

Ce module porte sur **une seule chose** : comprendre comment Python résout, exécute et expose le code réparti dans plusieurs fichiers et dossiers. Le sujet l'emballe dans une métaphore alchimique, mais derrière les potions il y a quatre mécanismes précis — les *quatre mystères sacrés* :

1. L'initialisation de package (`__init__.py`)
2. Les chemins d'import (`import` vs `from … import`)
3. Imports absolus vs relatifs
4. Les dépendances circulaires

L'objectif n'est pas de *faire marcher* les imports, mais de **comprendre pourquoi ils marchent (ou cassent)**. Ce README présente chaque notion avec son mécanisme sous-jacent, et finit par une section dédiée aux questions de défense.

---

## 0. La fondation : module, package, et la grande différence avec le C

Avant les quatre mystères, le socle. Si tu viens du C, le piège est de raisonner `import` comme `#include`. **Ce sont deux choses radicalement différentes.**

| | C : `#include` | Python : `import` |
|---|---|---|
| Quand ? | Au préprocesseur, avant compilation | À l'exécution (runtime) |
| Quoi ? | Copier-coller textuel du contenu | Exécuter le module **une fois**, puis lier un nom |
| Doublons | Gérés par les include guards | Gérés par un cache (`sys.modules`) |
| Résultat | Du texte injecté | Un **objet module** dans ta mémoire |

C'est la clé qui débloque tout le reste. Quand tu écris `import elements`, Python ne recopie pas le fichier : il **exécute** `elements.py` du début à la fin, fabrique un objet module, le range dans le cache, et lie le nom `elements` dans ton espace de noms. Cette nature *runtime* explique le cache, la sémantique des `from … import`, et surtout pourquoi les imports circulaires se comportent comme ils le font.

**Module** = un fichier `.py`.
**Package** = un dossier qui contient un `__init__.py`.

```python
def create_fire() -> str:
    return "Fire element created"
```

Ce fichier `elements.py` est un module. Le dossier `alchemy/` devient un package dès qu'on y pose un `__init__.py`.

## 1. Mystère I — `__init__.py` et l'initialisation de package

### Ce que `__init__.py` fait vraiment

On entend souvent « `__init__.py` transforme un dossier en package ». C'est vrai mais incomplet. Le vrai rôle :

- **Il s'exécute** au moment où le package est importé (la première fois).
- **Il définit l'interface publique** du package : ce qui est accessible via `import alchemy` ou `from alchemy import …`.

Autrement dit, `__init__.py` est une **vitrine curatée**. Ce qu'il importe et expose devient l'API du package ; ce qu'il n'expose pas reste invisible depuis l'extérieur du package, même si le code existe dans un sous-module.

```python
from alchemy.elements import create_air
from alchemy.potions import healing_potion, strength_potion

heal = healing_potion
```

Avec ce `__init__.py` :

- `alchemy.create_air()` fonctionne (importé dans la vitrine).
- `alchemy.create_earth()` **lève une `AttributeError`** — `create_earth` existe pourtant dans `alchemy/elements.py`, mais le `__init__.py` ne l'a pas importé. Il n'est donc pas dans l'espace de noms du package.

### La preuve dans le projet : `ft_alembic_4.py`

```
AttributeError: module 'alchemy' has no attribute 'create_earth'.
Did you mean: 'create_air'?
```

Cette erreur n'est pas un bug, c'est **la démonstration**. Le sujet la demande exprès : elle prouve que l'interface est curatée. `create_air` est exposé, `create_earth` non.

### L'alias de package : `heal`

La ligne `heal = healing_potion` montre qu'on peut exposer une fonction **sous un autre nom** à travers le package. `from alchemy import heal` donne accès à `healing_potion` rebaptisée. C'est ce que `ft_distillation_1.py` teste.

### `__all__`

Variable optionnelle qui définit ce que `from alchemy import *` exporte :

```python
__all__ = ["create_air", "healing_potion", "strength_potion", "heal"]
```

Sans `__all__`, `import *` ramène tous les noms ne commençant pas par `_`. Avec, tu contrôles exactement la liste. (Note : `import *` reste à éviter en code de prod ; ici c'est pédagogique.)

## 2. Mystère II — Les chemins d'import : `import` vs `from … import`

Deux structures, deux espaces de noms différents.

### `import module` → accès qualifié

```python
import elements

result: str = elements.create_fire()
```

Tu importes le **module entier**. Tu accèdes à son contenu en le préfixant (`elements.create_fire`). Avantage : pas de collision de noms, on voit toujours d'où vient une fonction. C'est la structure de `ft_alembic_0`, `ft_alembic_2`, `ft_alembic_4`.

### `from module import nom` → accès direct

```python
from elements import create_water

result: str = create_water()
```

Tu importes **un nom précis** dans ton espace de noms local. Tu l'appelles sans préfixe. Plus court, mais risque de collision si deux modules définissent le même nom. Structure de `ft_alembic_1`, `ft_alembic_3`, `ft_alembic_5`.

### Les alias

```python
import alchemy.elements as elems
from alchemy.potions import healing_potion as brew
```

`as` renomme localement, que ce soit un module ou un nom. Utile pour raccourcir des chemins longs ou éviter des collisions.

### Le point crucial : la sémantique « snapshot » de `from … import`

C'est LE détail que les gens ratent. `from X import Y` ne crée **pas** un lien vivant vers `X.Y`. Il **copie la référence courante** de `X.Y` dans ton espace de noms, au moment de l'import.

```python
from alchemy import heal     # 'heal' pointe vers ce que 'alchemy.heal' valait à cet instant
```

Conséquence : si plus tard quelqu'un réaffecte `alchemy.heal = autre_chose`, **ton `heal` local ne bouge pas** — c'est une liaison séparée, figée. À l'inverse :

```python
import alchemy
alchemy.heal()               # relit 'alchemy.heal' à chaque appel → voit toujours la valeur actuelle
```

Avec `import module`, l'accès à l'attribut est **différé au moment de l'appel** ; avec `from module import nom`, il est **fixé au moment de l'import**. Garde ça en tête : ça revient au cœur du Mystère IV.

## 3. Mystère III — Imports absolus vs relatifs

Deux façons d'écrire le chemin vers le même module.

### Import absolu

Le chemin complet depuis la racine du projet (un répertoire présent dans `sys.path`) :

```python
from alchemy.potions import strength_potion
from alchemy.elements import create_air
```

### Import relatif

Le chemin **par rapport au package courant**, avec des points :

- `.` = le package courant
- `..` = le package parent
- `...` = grand-parent, etc.

```python
from . import elements          # un module frère dans le même package
from .potions import healing_potion
from ..elements import create_air   # remonte d'un niveau
```

### Exemple concret : `recipes.py`

Le fichier `alchemy/transmutation/recipes.py` doit contenir **au moins un import absolu et un import relatif** (exigence du sujet). Depuis `transmutation/`, pour atteindre `alchemy/elements.py` et `alchemy/potions.py` :

```python
from alchemy.elements import create_air
from ..potions import strength_potion


def lead_to_gold() -> str:
    air: str = create_air()
    potion: str = strength_potion()
    return f"Recipe transmuting Lead to Gold: brew '{air}' and '{potion}'"
```

- `from alchemy.elements import create_air` → **absolu** (chemin complet).
- `from ..potions import strength_potion` → **relatif** (`..` remonte de `transmutation` à `alchemy`, puis descend dans `potions`).

> Subtilité du projet : la chaîne finale demande aussi `[created fire]`, qui vient du `elements.py` **racine** (hors package). Ce fichier racine n'est atteignable que parce que le répertoire du script lancé est dans `sys.path` — un import absolu `import elements` le trouve, mais seulement quand on exécute depuis la racine. C'est exactement le genre de fragilité que les imports absolus depuis la racine introduisent.

### Quand utiliser l'un ou l'autre ?

> *« When should an alchemist use absolute pathways vs relative pathways? »* — la question du sujet.

**Imports absolus** (recommandés par défaut, cf. PEP 8) :
- Sans ambiguïté, lisibles : on voit le chemin complet.
- Fonctionnent depuis n'importe où, y compris dans un script lancé directement.
- Inconvénient : verbeux, et cassent si tu renommes/déplaces le package racine.

**Imports relatifs** :
- Concis pour les imports **internes** à un package.
- Survivent à un renommage du package racine (le chemin interne ne change pas).
- Rendent explicite que l'import est intra-package.
- Inconvénient : **ne fonctionnent que dans un package**. Un fichier lancé directement (`python3 fichier.py`) n'a pas de contexte de package (`__package__` vide) → `ImportError: attempted relative import with no known parent package`.

Règle pratique : **absolu par défaut**, relatif pour les imports internes d'un package, surtout quand le chemin absolu devient long.

## 4. Mystère IV — Les dépendances circulaires (« Avoid the Explosion »)

### Qu'est-ce qu'un import circulaire ?

Module A importe B, et B importe A. Vu la nature *runtime* de l'import (Mystère 0), ça peut exploser — ou pas, selon **comment** tu importes.

### Le mécanisme exact de l'explosion

Quand Python importe un module, il fait, dans l'ordre :

1. Crée un objet module **vide**.
2. Le range **immédiatement** dans `sys.modules` (avant même de l'exécuter).
3. Exécute le code du module de haut en bas, ce qui remplit progressivement son contenu.

Le piège : à l'étape 3, si le module en cours fait `from autre import truc`, et que `autre` re-importe le premier… Python voit que le premier est **déjà dans `sys.modules`** (étape 2), donc il ne le ré-exécute pas. Il essaie juste d'y lire `truc`. **Mais le premier module n'a pas fini de s'exécuter** : si `truc` est défini *après* la ligne d'import qui a déclenché la chaîne, il n'existe pas encore.

### La preuve : `ft_kaboom_1.py` et le dark spellbook

```python
from .dark_validator import validate_ingredients


def dark_spell_allowed_ingredients() -> list[str]:
    return ["bats", "frogs", "arsenic", "eyeball"]
```

```python
from .dark_spellbook import dark_spell_allowed_ingredients


def validate_ingredients(ingredients: str) -> str:
    ...
```

Déroulé de l'explosion :

1. `ft_kaboom_1` fait `from …dark_spellbook import dark_spell_record`.
2. `dark_spellbook` commence, **ligne 2** : `from .dark_validator import validate_ingredients` → déclenche `dark_validator`.
3. `dark_validator` commence, **ligne 2** : `from .dark_spellbook import dark_spell_allowed_ingredients`.
4. `dark_spellbook` est déjà dans `sys.modules` (partiellement initialisé), mais `dark_spell_allowed_ingredients` est défini **après** sa ligne 2 → pas encore créé.

```
ImportError: cannot import name 'dark_spell_allowed_ingredients'
from partially initialized module 'alchemy.grimoire.dark_spellbook'
(most likely due to a circular import)
```

Le mot-clé du diagnostic : **partially initialized module**.

### Pourquoi la lumière survit et l'ombre explose

Même cycle, mais le `light_validator` importe **différemment**. C'est toute la nuance du Mystère II qui revient :

```python
from . import light_spellbook


def validate_ingredients(ingredients: str) -> str:
    allowed: list[str] = light_spellbook.light_spell_allowed_ingredients()
    ...
```

La différence décisive :

- Le dark fait `from .dark_spellbook import dark_spell_allowed_ingredients` → il réclame **le nom, tout de suite**, à l'import. Le nom n'existe pas encore → boom.
- Le light fait `from . import light_spellbook` → il récupère **l'objet module**, qui *existe déjà* dans `sys.modules` (même partiel). Puis il n'accède à `light_spell_allowed_ingredients` qu'au **moment de l'appel** de `validate_ingredients`, à l'exécution — quand tout est chargé.

> **Importer un nom = liaison immédiate. Importer un module et lire l'attribut = lecture différée.** C'est exactement la distinction `import x` vs `from x import y` du Mystère II, et c'est ce qui sauve le laboratoire.

### Les trois façons de casser un cycle

Le sujet dit « il y a plusieurs manières, choisis-en une, sache les expliquer ». Les voici :

1. **Importer le module, pas le nom** (`import x` / `from . import x`), puis accéder à l'attribut à l'appel. Différer la lecture suffit. *(C'est l'approche du light spellbook.)*
2. **Déplacer l'import dans la fonction** (import local / différé) :
   ```python
   def validate_ingredients(ingredients: str) -> str:
       from .light_spellbook import light_spell_allowed_ingredients
       allowed: list[str] = light_spell_allowed_ingredients()
       ...
   ```
   L'import ne s'exécute qu'à l'appel, plus au chargement.
3. **Restructurer** : sortir la dépendance partagée dans un troisième module. Si les deux dépendent d'un module commun (ex. la liste des ingrédients dans un `ingredients.py`), le cycle disparaît à la racine. C'est la solution la plus propre.

## 5. Annexe — Les mécanismes en coulisses

### `sys.modules` : le cache d'imports

Un dictionnaire `{ "nom_module": objet_module }`. Avant tout import, Python le consulte. Si le module y est, il réutilise l'objet ; sinon il l'exécute et l'y range. **C'est pourquoi le code de premier niveau d'un module ne s'exécute qu'une fois**, même importé dans dix fichiers. (Et c'est aussi l'étape 2 du mécanisme circulaire.)

### `__pycache__` et les `.pyc`

À l'import d'un module, Python le compile en bytecode et met le résultat en cache dans `__pycache__/module.cpython-310.pyc`. Au prochain import, si la source n'a pas changé (comparaison de date/hash), il recharge le `.pyc` directement et saute la recompilation.

- C'est de l'**optimisation**, pas un artefact à versionner → à mettre dans `.gitignore`.
- Le **script lancé** (le fichier en argument de `python3`) n'est **pas** mis en cache ; seuls les **modules importés** le sont.

### `__name__` et `if __name__ == "__main__"`

Quand un fichier est **lancé directement**, son `__name__` vaut `"__main__"`. Quand il est **importé**, `__name__` vaut le nom du module. D'où le garde classique pour qu'un fichier puisse servir à la fois de module importable et de script exécutable :

```python
if __name__ == "__main__":
    main()
```

## 6. Préparation à la défense

Le sujet prévient : *« you may be asked to explain import mechanisms, demonstrate different import styles, or modify your laboratory »*. Réponses prêtes :

**Q : Que fait exactement `__init__.py` ?**
Il s'exécute à l'import du package et définit son interface publique. Ce qu'il importe est exposé ; le reste reste invisible depuis l'extérieur.

**Q : Pourquoi `alchemy.create_earth()` lève une `AttributeError` ?**
Parce que `__init__.py` n'a pas importé `create_earth`. La fonction existe dans `alchemy/elements.py`, mais elle n'est pas dans l'espace de noms du package. Interface curatée.

**Q : Différence entre `import x` et `from x import y` ?**
`import x` ramène le module entier, accès qualifié `x.y`, lecture de l'attribut différée à l'appel. `from x import y` ramène un nom dans l'espace local, accès direct `y`, liaison figée à l'import (sémantique snapshot).

**Q : Absolu vs relatif, lequel choisir ?**
Absolu par défaut (lisible, marche partout, PEP 8). Relatif pour les imports internes d'un package, surtout si le chemin absolu est long. Les relatifs cassent dans un fichier lancé directement (pas de package parent).

**Q : Pourquoi le dark spellbook explose mais pas le light ?**
Cycle identique, import différent. Le dark importe un **nom** non encore défini (`from … import dark_spell_allowed_ingredients`) → `ImportError` sur module partiellement initialisé. Le light importe le **module** (qui existe déjà, même partiel) et ne lit l'attribut qu'à l'appel → tout est chargé à ce moment-là.

**Q : Cite trois façons de briser un cycle.**
(1) Importer le module au lieu du nom et différer l'accès ; (2) import local dans la fonction ; (3) extraire la dépendance partagée dans un troisième module.

## Les quatre mystères en une phrase

1. **`__init__.py`** est la vitrine curatée d'un package : il s'exécute à l'import et décide de ce qui est exposé.
2. **`import` vs `from … import`** : module entier + accès différé, ou nom précis + liaison figée.
3. **Absolu vs relatif** : chemin complet depuis la racine, ou chemin pointé depuis le package courant.
4. **Cycles** : importer un *nom* lie tout de suite (et peut exploser sur module partiel) ; importer un *module* et lire l'attribut plus tard sauve la mise.
