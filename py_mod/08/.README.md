## 0. La bascule : du langage à l'exploitation

Un point de cadrage avant les piliers. Jusqu'ici, une erreur = un bug de logique. Ici, une erreur = un **problème d'environnement** : la mauvaise version d'une lib, un secret committé, une config qui diffère entre dev et prod. Ces bugs-là ne se voient pas dans le code, ils se voient dans le *contexte d'exécution*.

### Le frame C

Deux des trois piliers ont un équivalent direct que tu connais :

- **Variables d'environnement** = `getenv()` / `environ[]`. Exactement le même mécanisme : le processus hérite d'un tableau de paires `CLE=valeur` de son parent (le shell). `os.environ.get("API_KEY")` en Python, c'est `getenv("API_KEY")` en C. Le fichier `.env` n'est qu'une **convention** pour peupler cet environnement avant que le programme le lise.
- **Reproductibilité des dépendances** = la différence entre « linker contre les libs système » (fragile, dépend de la machine) et « figer les versions exactes » (build reproductible, comme un lockfile). Un `poetry.lock`, c'est l'équivalent d'un build déterministe : tout le monde compile contre exactement les mêmes versions.

L'environnement virtuel, lui, n'a pas d'équivalent C strict : c'est un **namespace léger** pour les paquets Python — proche de l'idée d'un sandbox / d'un chroot, mais limité à `sys.prefix`.

## 1. Pilier I — Les environnements virtuels (ex0 / `construct.py`)

### Le problème

Le Python global est **partagé** par tous les projets de la machine. Le projet A veut `numpy 1.25`, le projet B veut `numpy 2.0` : conflit. Installer en global pollue le système, casse d'autres projets, et n'est souvent même pas permis (droits admin). D'où l'environnement virtuel : un espace de paquets **isolé**, jetable, propre à un projet.

### Ce que fait `python -m venv matrix_env`

Ça crée un dossier contenant :

- `bin/` (Unix) ou `Scripts/` (Windows) — un `python` et un `pip` propres au venv ;
- `lib/pythonX.Y/site-packages/` — là où `pip install` déposera les paquets, **isolé** du global ;
- `pyvenv.cfg` — un petit fichier de config qui contient `home = ...` pointant vers le Python système d'origine.

### Le mécanisme de détection — ton `is_in_venv()`

```python
def is_in_venv() -> bool:
    return sys.prefix != sys.base_prefix
```

C'est la méthode canonique, et voici *pourquoi* elle marche. Au démarrage, l'interpréteur trouve `pyvenv.cfg` à côté de l'exécutable et redirige `sys.prefix` vers le dossier du venv — **mais** garde `sys.base_prefix` pointant vers le Python système d'origine (via le `home` du `pyvenv.cfg`). Donc :

- **Hors venv** : `sys.prefix == sys.base_prefix` (même préfixe).
- **Dans un venv** : `sys.prefix` = le venv, `sys.base_prefix` = le système → ils diffèrent.

Ton `get_venv_name()` (`os.path.basename(sys.prefix)`) et ton `get_site_packages()` (`site.getsitepackages()[0]`) exploitent la même redirection : dans un venv, `site` renvoie le `site-packages` isolé.

### Ce que fait `source .../activate` (et ce qu'il ne fait *pas*)

`activate` est une **commodité** : il préfixe `PATH` avec le `bin/` du venv (pour que taper `python`/`pip` vise le venv), pose la variable `VIRTUAL_ENV`, et modifie le prompt `(matrix_env)`. Point important à savoir en revue : **l'isolation ne dépend pas de l'activation**. Si tu appelles directement `matrix_env/bin/python`, l'interpréteur lit quand même `pyvenv.cfg` et s'isole. Activer ne fait que t'éviter de taper le chemin complet. Le vrai mécanisme, c'est `pyvenv.cfg`, pas `activate`.

### Pourquoi ne pas committer le venv

Le sujet l'exige. Trois raisons : il est **régénérable** (`python -m venv` + install le recrée), il est **spécifique à la plateforme** (les binaires d'un venv Linux ne marchent pas sous Windows/Mac), et il est **volumineux**. Ce qu'on committe, c'est la *recette* (`requirements.txt` / `pyproject.toml`), pas le résultat.

## 2. Pilier II — pip vs Poetry (ex1 / `loading.py`)

### Le problème

Un vrai projet a des dépendances, qui ont elles-mêmes des dépendances (transitive). Deux enjeux : **résoudre** un ensemble de versions compatibles, et le rendre **reproductible** (que ton collègue installe exactement la même chose). C'est le *dependency hell* que pip et Poetry gèrent différemment.

### Détection gracieuse des dépendances — ton `check_dependencies()`

Plutôt qu'un `import pandas` en tête (qui crash immédiatement si absent), tu importes dynamiquement et tu attrapes l'échec :

```python
try:
    mod = importlib.import_module(pkg)
    version: str = getattr(mod, "__version__", "unknown")
    print(f"[OK] {pkg} ({version})")
    loaded[pkg] = mod
except ImportError:
    print(f"[MISSING] {pkg} - not installed")
    missing.append(pkg)
```

Deux notions ici : `importlib.import_module(nom)` importe par **chaîne** à l'exécution (utile quand le nom est dans une variable/boucle), et le `try/except ImportError` permet la **dégradation gracieuse** — afficher un message utile au lieu de planter. C'est exactement ce que le sujet demande (« handle missing dependencies gracefully »).

### `requirements.txt` (pip) vs `pyproject.toml` + `poetry.lock` (Poetry)

C'est **la** notion centrale de l'exercice. La différence n'est pas cosmétique, c'est **déclaré vs verrouillé** :

| | pip (`requirements.txt`) | Poetry (`pyproject.toml` + `poetry.lock`) |
|---|---|---|
| Rôle du fichier | Liste plate de paquets | `pyproject.toml` = intention (plages) ; `poetry.lock` = résolution exacte |
| Résolution du graphe | Manuelle / au coup par coup | Automatique, arbre complet résolu |
| Reproductibilité | Non garantie (sauf `pip freeze` → `==`) | **Garantie** par le lock (versions exactes, transitives incluses) |
| Gestion du venv | Séparée (à toi de la faire) | Intégrée (`poetry install` gère le venv) |
| Standard | Fichier ad hoc | `pyproject.toml` = standard PEP 518/621 |

Le point clé à dire en revue : `requirements.txt` avec `>=` (comme le tien) exprime une **contrainte lâche** — deux installs à deux dates peuvent différer. Pour un pip *reproductible*, il faut `pip freeze > requirements.txt` (versions exactes `==`). Poetry résout ce problème *par construction* : `pyproject.toml` déclare les plages, `poetry.lock` fige le résultat, et committer le lock garantit des installs identiques partout. **pip = simple et universel ; Poetry = reproductible et complet.**

### SemVer — les opérateurs de tes fichiers

```
pandas>=2.0.0      (ton requirements.txt) : 2.0.0 ou plus, y compris 3.x → large
pandas = "^2.0.0"  (ton pyproject.toml)   : >=2.0.0, <3.0.0 → compatible major
```

À connaître : `^` (caret) autorise tout ce qui ne change pas le premier chiffre non nul (ici le major → `<3.0.0`) ; `~` (tilde) est plus strict (`~2.0.0` → `>=2.0.0,<2.1.0`, patch seulement) ; `==` fige exactement. Le caret est le défaut Poetry car il capte les correctifs/features sans risquer une rupture majeure.

## 3. Pilier III — Variables d'environnement & `.env` (ex2 / `oracle.py`)

### Le problème

Une appli a besoin de secrets (clés API, URL de base de données) et de réglages qui **changent selon l'environnement** (dev vs prod). Les écrire en dur dans le code, c'est deux fautes : impossible de changer sans redéployer, et surtout **le secret finit dans Git**, visible par tous et dans l'historique pour toujours. La solution : la config vit dans **l'environnement**, pas dans le code.

### L'environnement de processus — ton `load_config()`

```python
def load_config() -> dict[str, str]:
    config: dict[str, str] = {}
    for key, default in DEFAULTS.items():
        config[key] = os.environ.get(key, default)
    return config
```

`os.environ` est le tableau des variables d'environnement héritées du shell (le `environ` du C). `.get(key, default)` lit la variable ou retombe sur un défaut — ta gestion des valeurs manquantes est là.

### `python-dotenv` et la précédence — le point subtil

Le sujet impose `python-dotenv` (« pas de parser maison »). Ton import gardé :

```python
try:
    from dotenv import load_dotenv
    load_dotenv()
except ImportError:
    print("Warning: python-dotenv not installed. Using environment variables only.")
```

Ce qu'il faut comprendre et **savoir expliquer** : `load_dotenv()` lit le fichier `.env` et injecte ses paires dans `os.environ`, **mais par défaut n'écrase pas** une variable déjà présente (`override=False`). D'où la **précédence** :

```
variable réelle du shell   >   valeur du .env   >   défaut dans le code
```

C'est *exactement* pourquoi ton exemple d'override marche : `MATRIX_MODE=production python3 oracle.py` met la variable dans `os.environ` **avant** `load_dotenv()`, donc le `.env` ne l'écrase pas, et `os.environ.get` renvoie `production`. Ce n'est pas un hasard, c'est le comportement `override=False` de dotenv. Excellente question de revue.

### Dev vs prod : même code, environnement différent

Ton `main()` branche sur `MATRIX_MODE` (`[PROD]` / `[DEV]`). C'est le principe **12-factor de la config** : un seul code, zéro `if` métier en dur sur l'environnement de déploiement — juste une variable qui change. Le même binaire tourne en dev et en prod ; seul l'environnement diffère.

### Secrets & sécurité — `.env` dans `.gitignore`, et `.env.example`

Le sujet insiste : *« you must be able to explain why »*. Voilà le pourquoi :

- **`.env` va dans `.gitignore`** parce qu'il contient les vrais secrets. Committé, un secret est exposé à quiconque a accès au repo, **et reste dans l'historique Git pour toujours** (même supprimé plus tard) — donc irrévocable sans réécrire l'historique. Il faudrait le *roter* (le changer partout), coûteux.
- **`.env.example` est committé** : c'est le **template** — les mêmes clés (`MATRIX_MODE`, `DATABASE_URL`, `API_KEY`…) mais avec des valeurs vides ou factices. Il documente *quelles* variables ton programme attend, sans jamais exposer *leurs valeurs*. Un nouveau venu fait `cp .env.example .env`, remplit ses propres secrets, et démarre.

La règle d'or : **la structure de la config est publique, ses valeurs sont privées.**

## 4. Les mécanismes en coulisses

### venv, en interne

Un venv n'est pas une copie de Python : c'est essentiellement un dossier `site-packages` isolé + un `pyvenv.cfg` qui dit à l'interpréteur « ton `base_prefix` est là-bas, ton `prefix` est ici ». La détection (`sys.prefix != sys.base_prefix`) et l'isolation des paquets découlent toutes de cette redirection lue au démarrage.

### `importlib.import_module` vs `import`

`import x` est statique (résolu à l'écriture, le nom est littéral). `importlib.import_module("x")` est dynamique (le nom est une chaîne, calculable à l'exécution). Le second permet d'itérer sur une liste de paquets et de gérer proprement les absents — ce que fait ta boucle.

### `os.environ` et `load_dotenv(override=...)`

`os.environ` reflète l'environnement du processus. `load_dotenv()` le complète depuis `.env` sans écraser l'existant (`override=False`), ce qui établit la hiérarchie shell > .env > défaut. Passer `override=True` inverserait la priorité (le `.env` gagnerait) — à ne faire qu'en connaissance de cause.

## 5. Le fil rouge : Twelve-Factor & séparation config/code

Les trois piliers servent la même idée — un système **reproductible, portable et sécurisé** — et correspondent à des facteurs de la méthodologie *Twelve-Factor App* :

- **Isolation** (venv) → chaque déploiement part d'un environnement propre et déterministe.
- **Dépendances explicites** (pip/Poetry) → jamais de dépendance implicite au système ; tout est déclaré (et idéalement verrouillé).
- **Config dans l'environnement** (`.env`/env vars) → le code est identique partout ; seule la config injectée change, et les secrets ne touchent jamais le dépôt.

C'est le socle « ops » du métier : ce qui rend un projet installable par un inconnu, déployable en prod, et non fuyant côté secrets.

## 6. Préparation à la peer-review

Le sujet liste précisément ce que tu dois démontrer. Réponses prêtes :

**Q : Qu'est-ce qu'un environnement virtuel et pourquoi c'est important ?**
Un espace de paquets isolé, propre à un projet, régénérable. Il évite les conflits de versions entre projets, ne pollue pas le Python global (ni ne requiert les droits admin), et rend l'installation reproductible. Techniquement : une redirection de `sys.prefix` via `pyvenv.cfg`, détectable par `sys.prefix != sys.base_prefix`.

**Q : Différence entre pip et Poetry ?**
pip installe depuis une liste plate (`requirements.txt`) sans garantie de reproductibilité ni gestion du venv — simple et universel. Poetry résout le graphe complet, fige les versions exactes dans `poetry.lock` (installs déterministes), sépare l'intention (`pyproject.toml`) du verrou (`poetry.lock`), et gère le venv. En un mot : **déclaré vs verrouillé**, simplicité vs reproductibilité.

**Q : Comment les variables d'environnement sécurisent et configurent une appli ?**
Elles sortent les secrets et les réglages du code : le même code tourne en dev et en prod, seule la config injectée change (12-factor). Les secrets vivent dans un `.env` non committé, chargé par `python-dotenv`, avec une précédence shell > .env > défaut.

**Q : Pourquoi `.env` dans `.gitignore` ?**
Parce qu'il contient les vrais secrets. Committé, ils sont exposés à tout le repo et persistent dans l'historique Git à jamais (irrévocable sans rotation). On committe `.env.example` (mêmes clés, valeurs factices) pour documenter la structure sans les valeurs.

**Q : Pourquoi l'override en ligne de commande fonctionne-t-il ?**
Parce que `load_dotenv()` n'écrase pas (`override=False`) une variable déjà dans `os.environ`. Une variable posée avant l'exécution (`MATRIX_MODE=production python3 oracle.py`) l'emporte donc sur le `.env`.

**Q : Pourquoi ne pas committer le venv ?**
Régénérable, spécifique à la plateforme, volumineux. On committe la recette, pas le résultat.

Ton code est solide et conforme aux modules autorisés. Trois détails purement flake8 valent le coup d'être corrigés, parce que le reviewer va lancer flake8 et que la tolérance de l'ex1 ne couvre **que** les erreurs d'import (pas ces cas-là), et l'ex2 n'a aucune tolérance :

Tu peux simplement supprimer cette ligne et garder `import matplotlib.pyplot as mplt`.

Rien de conceptuel, juste deux `f` et une ligne morte pour être 100 % flake8-clean.
